= Client quota throughput: simple client
:page-layout: lab
:env-docker: true
:page-categories: Management, Monitoring
:description: See how a configured consumer_byte_rate quota translates into real observed throughput, with a plain Kafka client.

The number you configure in a `consumer_byte_rate`/`producer_byte_rate` quota is not the number you'll observe. Real throughput overshoots the nominal quota, and below a certain quota value, it stops dropping further no matter how much you lower it. This lab lets you see that directly, with a plain Kafka client, and gives you a formula to predict it ahead of time.

== Prerequisites

* Docker and Docker Compose
* Python 3 (only if you want to run `expected_throughput.py` from your host instead of inside the `python-client` container)

== Limitations

* This lab runs Redpanda in `--mode dev-container` with a single broker (`--smp 1`). It's for learning the mechanism, not for measuring production throughput ceilings.
* Quotas are enforced per broker. This lab is single-broker specifically so the configured quota and the observed per-connection rate are directly comparable without dividing across brokers.
* The formula is a rule of thumb derived from Redpanda's documented token-bucket enforcement, calibrated for *this lab's specific setup* (3 partitions, default `confluent-kafka`/librdkafka fetch settings, ~1.7KB records). Real overshoot also depends on your own client's fetch/batch settings, record size, and partition count. The "Try different values" section below shows you how to recalibrate for your own numbers rather than trusting this lab's constant blindly.
* Requires Redpanda v26.2.1 or later (for `kafka_per_entity_quota_metrics`, used in the "Go deeper" section).

== Run the lab

. Clone this repository:
+
```bash
git clone https://github.com/redpanda-data/redpanda-labs.git
```

. Change into the `docker-compose/client-quota-throughput/simple-client/` directory:
+
[,bash]
----
cd redpanda-labs/docker-compose/client-quota-throughput/simple-client
----

. Start the stack:
+
[source,bash]
----
cp .env.example .env
docker compose up -d
----

. Create the topic and seed a backlog big enough to sustain the test window:
+
[source,bash]
----
docker compose exec redpanda-0 rpk topic create quota-demo -p 3
docker compose exec python-client python3 /scripts/client.py produce \
  --topic quota-demo --num-records 200000 --record-size-bytes 1700 \
  --client-id quota-demo-client
----

. Apply a quota well below the breakpoint, to see the floor effect:
+
[source,bash]
----
docker compose exec redpanda-0 rpk cluster quotas alter \
  --add consumer_byte_rate=10000 --name client-id=quota-demo-client
----

. Predict what you should actually observe, using this lab's calibrated constant, measured for this exact 3-partition/default-fetch-settings/1.7KB-record setup (see "Try different values" to recalibrate for your own):
+
[source,bash]
----
python3 scripts/expected_throughput.py --quota-bytes-per-sec 10000 \
  --record-size-bytes 1700 --slip-through-bytes 13963380
----
+
```
Slip-through size (S): 13,963,380 bytes  [calibrated]
Breakpoint (R*  =  S / throttle_delay_cap): 465,446 bytes/sec
Regime: floor
Predicted actual throughput (A): 465,446 bytes/sec (273.8 records/sec at 1,700B records)

You configured R=10,000 B/s, well below the breakpoint. Lowering R further will NOT reduce
throughput below ~465,446 B/s. To go lower, shrink the client's own fetch.max.bytes /
max.partition.fetch.bytes, or lower --throttle-delay-cap-sec (max_kafka_throttle_delay_ms)
instead.
```

. Watch the real throughput live, in another terminal, while the next step runs:
+
[source,bash]
----
watch -n1 'docker compose exec -T redpanda-0 rpk cluster connections list \
  --client-id=quota-demo-client \
  --order-by="recent_request_statistics.fetch_bytes desc"'
----

. Consume, and compare the self-reported rate to the prediction above:
+
[source,bash]
----
docker compose exec python-client python3 /scripts/client.py consume \
  --topic quota-demo --group-id quota-demo-floor --duration-sec 95 \
  --client-id quota-demo-client
----
+
`--duration-sec 95` (not 60) is deliberate. The throttle delay here is capped at 30s, and a
window shorter than about 3x that cap can catch only one early burst and badly overstate the
rate (see `scripts/calibration_sweep.py`'s own comments for the full explanation).
+
This exact setup measured `bytes_per_sec=465,446 records_per_sec=273.8`, matching the
prediction and roughly *47x* the nominal 10,000 B/s quota, not a small rounding error.

== Try different values

Quota changes are live. No restart needed. Re-seed a fresh backlog of the same size before
each new trial (otherwise you're measuring against whatever's left of the old one, not a
fair comparison), then repeat the apply/predict/observe steps with a new value:

[source,bash]
----
docker compose exec python-client python3 /scripts/client.py produce \
  --topic quota-demo --num-records 200000 --record-size-bytes 1700 --client-id quota-demo-client
docker compose exec redpanda-0 rpk cluster quotas alter \
  --add consumer_byte_rate=2000000 --name client-id=quota-demo-client
----

At 2,000,000 B/s (well above the breakpoint), measured throughput on this setup came in at
`2,223,809 B/s`, close to the configured value and confirming the "nominal" regime where the
quota works about as you'd expect.

To recalibrate `S` for your *own* client/record-size/partition count instead of reusing this
lab's constant, run the floor-regime steps above with your own settings. Then
`S = measured_bytes_per_sec x throttle_delay_cap_sec` (default cap is 30s).

== Calibration results

A light calibration sweep (`scripts/calibration_sweep.py`, results in `calibration.csv`) across a
range of quota values, two fetch-size configurations, and three `max_kafka_throttle_delay_ms`
settings confirms the model's shape, not just the one worked example above:

|default fetch settings

|default fetch settings

|5,000 B/s

|shrunk fetch settings
|20,000 B/s
|76,063 B/s
|3.8x

|shrunk fetch settings

|1.3x

|shrunk fetch settings
|300,000 B/s

|shrunk fetch settings
|1,000,000 B/s
|1,014,770 B/s
|1.0x (nominal)
|===

Two things this confirms directly, not just in theory:

* The floor is flat, not proportional to R. At default fetch settings, R=5,000/20,000/80,000 all land in roughly the same 510,000-530,000 B/s band, so lowering the quota by 16x (80,000 -> 5,000) barely moved `A`. Only once R climbs past the breakpoint (between 300,000 and 1,000,000 here) does `A ~= R` kick in.
* Shrinking the client's own fetch settings is a real, working lever. The same quota values against shrunk fetch settings land in a much lower ~76,000-103,000 B/s floor band, about 5-7x lower than the default-settings floor. If you need a tighter real-world cap than the quota alone gives you, this is the knob that actually moves it.

`max_kafka_throttle_delay_ms` confirmation (fixed at R=20,000, default fetch settings):

[cols="1,1,1"]
|===
|D_cap |Actual (A) |Implied S (`A x D_cap`)

|10s
|1,250,105 B/s
|~12.5 MB

|30s (default)
|511,470 B/s footnote:[Same trial as the default-fetch-settings, R=20,000 row above. The default-D_cap case isn't run twice.]
|~15.3 MB

|60s
|199,804 B/s
|~12.0 MB
|===

The floor clearly moves in the predicted direction as `D_cap` changes (higher cap -> lower floor), and the implied `S` stays in the same general 12-15 MB range across all three, consistent with the model and in the same range as the 13,963,380-byte `S` calibrated from the worked example above, though not perfectly constant. That's expected for a light, single-trial-per-point calibration. Treat the exact numbers as order-of-magnitude guidance, not a precise SLA. A full statistically-rigorous fit (more trials per cell, more record sizes and partition counts) would tighten this further; see `calibration.csv` for the raw data if you want to extend it.

== Go deeper

To see the per-client-id metrics directly, rather than the live connection view:

[source,bash]
----
docker compose exec redpanda-0 rpk cluster config set kafka_per_entity_quota_metrics true
docker compose exec python-client python3 -c "
import urllib.request
data = urllib.request.urlopen('http://redpanda-0:9644/public_metrics').read().decode()
print('\n'.join(l for l in data.splitlines() if 'quota_client_id=\"quota-demo-client\"' in l))
"
----

These series (`redpanda_kafka_quotas_client_quota_throughput_by_entity`,
`..._throttle_time_ms_by_entity`) only appear *after* the entity has actually been throttled
at least once. If you don't see them, the quota you configured never matched your client's
traffic (check the client-id matches exactly).
