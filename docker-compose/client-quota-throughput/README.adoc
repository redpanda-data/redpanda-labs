== Overview

Redpanda's byte-rate client quotas (`consumer_byte_rate`, `producer_byte_rate`) never produce exactly the configured value in practice. Real observed throughput can overshoot the nominal quota by one or two orders of magnitude. And below a certain quota value, lowering it further stops helping at all. This is expected behavior given how quotas are enforced, but it causes confusion if you don't know the mechanism.

This lab has two variants that shows how this works in practice:

* xref:simple-client/README.adoc[simple-client] - a plain Kafka producer/consumer. Start here.
* xref:flink/README.adoc[flink] - the same thing with Apache Flink, which has an extra consideration: its Kafka source never joins a classic consumer group, so `rpk group describe` / consumer-group tooling can't be used to verify behavior.

=== The mechanism

Redpanda enforces a client quota as a token bucket. Capacity and refill rate both equal the configured quota `R` (bytes/sec). Enforcement happens *between* requests, where a request is equal to a full Fetch response or Produce request of size `S`. This size is bounded by the client's request-size settings (`fetch.max.bytes`/`max.partition.fetch.bytes` for consumers, batch size for producers).
Each broker will calculate a delay to apply to the client's next request based on how over or under the client's rate is in comparison to its quota between each request. That delay is also capped by `max_kafka_throttle_delay_ms` (default 30 seconds), which is a fail-safe so throttling never causes a client-side request timeout.

Put together, there's a sharp knee at `R* = S / throttle_delay_cap`:

[cols="1,2,2"]
|===
|Regime |Condition |What you'll observe

|Unconstrained
|`R` at or above the client's own max capability
|The client's own ceiling - the quota isn't the limit.

|Nominal
|`R*` <= `R` < client's own ceiling
|Throughput tracks `R`, about as you'd expect.

|Floor
|`R` < `R*`
|Throughput flattens out at `S / throttle_delay_cap` and stops dropping as you lower `R` further.
|===

With the `simple-client` lab at a 10,000 B/s quota (well below the knee for that lab's default setup), real throughput came in at *366,172 B/s* - about *37x* the configured value, and landing almost exactly on this formula's predicted floor (`S=10,985,205 bytes / 30s = 366,174 B/s`).

=== Predicting it yourself

Each variant ships `scripts/expected_throughput.py`, which implements the model above:

[source,bash]
----
python3 scripts/expected_throughput.py --quota-bytes-per-sec 10000 --record-size-bytes 1700
----

Without a calibrated `--slip-through-bytes`, it reports a *structural estimate* of `S` from your fetch/batch settings. This is useful as a starting point, but each variant's README shows you how to measure the real value for your own setup.
