= Fail the shadow topics over
:page-layout: solution-step

== Why

Failover is a separate, explicit step from the client move because the two answer different questions. Envoy answers "which cluster can serve this connection", automatically, in seconds, and reversibly. `rpk shadow failover` answers "is the source cluster gone for good", and there is no automatic answer to that: a cluster that is unreachable for thirty seconds during a network event must not be replaced, and a proxy cannot tell the difference. Making the promotion manual is what keeps a blip from becoming a split brain.

Once the topics are promoted the link stops fetching, so the shadow cluster is no longer tracking the source. If the source cluster came back now, its records after the last replicated offset would exist nowhere on the shadow cluster, and the two logs would have diverged. That is why this step is last and why it cannot be undone.

== Why Redpanda

Promotion is a state change, not a copy. The data is already in the shadow topic's partitions at the source's offsets, so failing over three partitions takes as long as an Admin API call: each partition stops its replication fetcher and starts accepting produce requests, and the next record is appended at the offset after the last replicated one. The consumer group's committed offsets are already in the shadow cluster's `__consumer_offsets`, so the group resumes without being told anything. See xref:streaming:manage:disaster-recovery/shadowing/failover.adoc[] and xref:streaming:reference:rpk/rpk-shadow/rpk-shadow-failover.adoc[].

== What happens inside

`rpk shadow failover --all` asks the shadow cluster's Admin API to move every topic of the link from `ACTIVE` through `FAILING_OVER` to `FAILED_OVER`. For each partition, the fetcher that was reading from the source stops and the partition becomes an ordinary leader that accepts produce requests. The link itself stays, with its topics in `FAILED_OVER`, so `rpk shadow status` remains the record of what happened; delete the link when you no longer need it.

The client then produces `ord-0013` to `ord-0018`, which are appended after the replicated records on the same three partitions. When the `dr-consumers` group rejoins, the coordinator on the shadow cluster hands it the committed offsets the link replicated, so it starts at partition 0 offset 4, partition 1 offset 6, and partition 2 offset 2, and reads only the six new records.

Six records, not eighteen: the group resumed from the offsets the link replicated instead of reprocessing the topic. If it reads 18 records, the offsets did not arrive before the failover, which means the group's id does not match the link's group filter. If it reads 0, the group was already advanced to the end of the topic by an earlier run; `make clean` and start again.
