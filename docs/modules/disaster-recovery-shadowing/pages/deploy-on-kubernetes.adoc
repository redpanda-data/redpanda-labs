= Deploy the same topology on Kubernetes
:page-layout: solution-step
:description: Run the same two clusters and the same shadow link on Kubernetes with the Redpanda Operator, as Redpanda and ShadowLink resources, and repeat the consumer group failover there.
:page-solution-step-duration: 20

Everything so far ran in Docker Compose, where a shadow link is a command you run. On Kubernetes it is a resource the Redpanda Operator reconciles, which means the disaster recovery topology is part of the cluster's desired state and survives the person who set it up. This step deploys both clusters and the link from three manifests and repeats the consumer group failover against them.

The commands here need a Kubernetes cluster, so they are not part of this solution's test run: a local Kubernetes cluster running the operator and two Redpanda clusters does not fit alongside the compose stack the earlier steps leave running. The manifest check in the first instruction does run on every test pass, and it is what keeps these manifests honest.

== Why

There is no Envoy here. On Kubernetes the client-routing half of this design is usually a Service, an Ingress, or a service mesh rather than a proxy you deploy yourself, so putting Envoy in the manifests would teach the wrong lesson about a platform that already has that layer. What Kubernetes changes is the other half: the clusters and the link become declared state.

The link lives in the shadow cluster's namespace because that is where it runs, and it names the source cluster by its in-cluster DNS name across namespaces. In a real deployment the two clusters are in different Kubernetes clusters, usually in different regions, and the `sourceCluster` addresses are whatever exposes the source cluster to the shadow cluster: an external listener, a load balancer, or a private link.

== Why Redpanda

The operator takes the same link that `rpk shadow create` takes, with the same options under different names, so the design does not change when the platform does. A `ShadowLink` resource is reconciled continuously: if the link is missing, the operator creates it, and if someone changes the filters in Git, the change reaches the cluster the same way every other change does. See xref:streaming:reference:k-crd.adoc[] and xref:streaming:deploy:redpanda/kubernetes/index.adoc[].

== What happens inside

The operator watches `Redpanda` and `ShadowLink` resources. For each `Redpanda` it renders and applies the Redpanda Helm chart, so a StatefulSet, its Services, its Console, and its configuration come from the `clusterSpec` in the manifest, and it sets the resource's `Ready` condition when the cluster reports healthy. For the `ShadowLink` it calls the shadow cluster's Admin API, creating or updating the link so that it matches the spec, sets the `Synced` condition, and reports the link's state in the resource's status, where `kubectl get shadowlink` reads it.

The field names differ from the `rpk` configuration even though the link is the same: the operator spells the prefix pattern `prefixed` where `rpk` spells it `PREFIX`, and `startOffset: earliest` is `start_at_earliest`. `make kubernetes-plan` checks both spellings, because a `patternType` the operator does not accept is rejected only when you apply the resource.

== In production

[.production-note]
The two clusters belong in two Kubernetes clusters, in separate regions, with TLS and SASL on both and the link's credentials scoped to what it replicates, and the manifests belong in Git so that the recovery topology is reviewed like any other change. See xref:streaming:deploy:redpanda/kubernetes/k-production-deployment.adoc[] and the Security row in xref:index.adoc#_production_considerations[Production considerations].
