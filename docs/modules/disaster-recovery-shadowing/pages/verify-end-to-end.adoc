== Why

A recovery you cannot verify is a recovery you have to take on trust, and the parts that matter most are the hardest to check afterwards. By the time this script runs, the source cluster is gone, so nothing can measure whether the two clusters were at parity before the outage or whether a reader really worked while the source was down.

So each step records what it measured, at the moment it measured it, into `state/`, and this script asserts those recorded facts alongside what it can still measure live. That is why the checks about the state before and during the outage are as exact as the ones about the end state.

== Why Redpanda

The claims are checkable because the primitives are exact. Offsets are preserved, so a watermark on one cluster can be compared with a watermark on the other. Committed offsets are replicated rather than approximated, so "the group resumed where it stopped" is an equality, not an estimate. Shadow topic state is reported per topic, so `FAILED_OVER` is something the script reads rather than infers. See xref:streaming:manage:disaster-recovery/shadowing/monitor.adoc[].

== What happens inside

The script sources `tools/verify-lib.sh` for its assertions, reads the recorded facts through a small helper that runs inside the client container so that the host needs no JSON tooling, and measures the rest against the shadow cluster, Envoy's admin API, and the shadow Console. Its 23 checks fall into eight groups: what is left standing, the state before the outage, replication parity, the replicated consumer offsets, client continuity during the outage, the failover, the consumer resuming, and the end state of the topic.

== In production

[.production-note]
The equivalent of this script is a scheduled failover rehearsal against a real pair of clusters, with the same assertions and a report that someone reads. See the Disaster recovery row in xref:index.adoc#_production_considerations[Production considerations].
