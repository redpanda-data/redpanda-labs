= Route clients through Envoy
:page-layout: solution-step
:description: Produce and consume orders through the Envoy proxy while the source cluster is healthy, then prove that the records and the consumer group's offsets both reached the shadow cluster.
:page-solution-step-duration: 8

The client has one address, `envoy:9092`, and it is about to use it for everything: producing the orders, reading them as a consumer group, and later reading them again from a different cluster. In this step the source cluster is the one behind that address, and you prove that the shadow cluster is keeping up.

== Why

Replication parity is a claim you check before you need it, not after. Lag reported by the link is a good signal, but the question a recovery plan has to answer is "does the other cluster hold my records", so `make parity` asks the two clusters instead of asking the link about itself. It compares high watermarks partition by partition, because a total that matches while one partition is behind is exactly the failure a total would hide.

The consumer offsets are checked separately, in the Verify step, because they travel on a different task of the same link and can lag behind the records. A recovery that has the data but not the offsets still works; it just costs you a reprocessing run that nobody planned for.

== Why Redpanda

The shadow topic preserves the source's offsets, so partition 1 offset 5 is the same record on both clusters and the replicated committed offsets need no translation. That is what makes a consumer's resume point portable, and it is why `make parity` can compare raw watermarks and mean something. See xref:streaming:develop:consume-data/consumer-offsets.adoc[] and xref:streaming:manage:disaster-recovery/shadowing/monitor.adoc[].

== What happens inside

The client asks Envoy for metadata about `dr-orders`. Envoy forwards the request to the source cluster, parses the response, and rewrites the address of broker 0 from `redpanda-source:9092` to `envoy:9092` before passing it on. The client then opens its produce connections to that address, so they arrive at Envoy too, and Envoy forwards each one to whichever endpoint it currently considers healthy. Redpanda hashes each record's key to pick a partition, which is why the 12 orders land 4, 6, and 2 across the three partitions on every run.

----

----

The offsets on the shadow cluster are the same numbers the group committed on the source. If the script times out, the group filter does not match: the link replicates groups whose ids start with `dr-`, and the group here is `dr-consumers`. If the offsets differ by a few records, the sync task has not caught up; the script polls for two minutes, so a timeout means something is wrong rather than slow.

== In production

[.production-note]
Parity and offset lag are monitored continuously rather than checked by hand, and alerting on them is what tells you whether a failover is safe on the day. See the Observability row in xref:index.adoc#_production_considerations[Production considerations].
