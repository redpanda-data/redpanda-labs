= Create the topics
:page-layout: solution-step
:description: Create the four topics with explicit partition counts, keys, and retention, and see how the key decides which consumer instance owns a player.
:page-solution-step-duration: 5

You create four topics with `rpk`. Each has a deliberate partition count and a stated key, because those two choices decide how far each consumer can scale and which guarantees the consumers in the later steps can rely on.

== What you do

. Create the topics. `make topics` runs these four commands and is safe to repeat:
+
[,bash]
----
make topics
----
+
[,makefile]
----
include::example$Makefile[tags=topics]
----

. Look at one of them:
+
[,bash]
----
docker compose exec -T rpk rpk topic describe game.player-events -c
----
+
`retention.ms` is `604800000` (7 days) and `cleanup.policy` is `delete`.

The four topics and the reason for each shape:

[cols="2,1,1,3"]
|===
| Topic | Partitions | Key | Why

| `game.player-events`
| 6
| `player_id`
| Everything about one player, in order, on one partition. Six partitions is the ceiling for the leaderboard group; xref:scale-and-replay.adoc[] runs three members.

| `game.match-events`
| 3
| `match_id`
| Match lifecycle. Written by the simulator, read by Redpanda Connect for the history table.

| `game.achievements`
| 3
| `player_id`
| Written by the achievements service. Same key as the source, so a player's achievements are ordered too.

| `game.player-events.dlq`
| 1
| original key
| Records the Connect pipeline could not process. One partition is plenty for something that should stay empty.
|===

== Why

The leaderboard and the achievements service are both correct only because the record key is `player_id`. The achievements service (xref:detect-achievements.adoc[]) keeps a small in-memory state per player and never consults a shared store. That is safe only if every event of one player reaches exactly one instance, in the order it was produced. Keying by `player_id` gives that. Keying by `match_id` on `game.match-events` gives the same guarantee for matches, which is what a history sink wants.

The partition counts are the scaling limits. A consumer group cannot have more active members than partitions, so six partitions means the leaderboard can run six instances, no more. Retention on `game.player-events` is 7 days because xref:scale-and-replay.adoc[] replays it; the default would do for the demo, but in a real game the replay window is a product decision.

== Why Redpanda

Topic creation is one `rpk topic create` with the partition count, the replication factor, and any topic property inline, and the same command works against Redpanda Cloud. Partition counts can be raised later with `rpk topic add-partitions`, but not lowered, so the key and the count are worth deciding up front. See xref:streaming:develop:manage-topics/index.adoc[] and xref:streaming:reference:rpk/rpk-topic/rpk-topic-create.adoc[].

== What happens inside

`rpk` sends a `CreateTopics` request to the broker. For each topic the controller creates the partitions as Raft groups (one replica each here, three in production), assigns leaders, and writes the topic properties to the controller log. From now on, every record the simulator produces with key `p014` lands on the same partition, because the producer hashes the key to choose one (xref:streaming:develop:produce-data/configure-producers.adoc[]). With 24 players and 6 partitions the spread is uneven (one partition can stay empty), which is normal for a small key space.

The simulator notices the topics within two seconds and moves from `waiting_for_topics` to `waiting_for_schema`. It still produces nothing.

== Verify

Run:

[,bash]
----
docker compose exec -T rpk rpk topic list
----

Expected output:

[.solution-verify]
[,text]
----
NAME                    PARTITIONS  REPLICAS
_schemas                1           1
game.achievements       3           1
game.match-events       3           1
game.player-events      6           1
game.player-events.dlq  1           1
----

`_schemas` is Schema Registry's own storage topic. If a topic shows a different partition count, you created it earlier with other settings: `rpk topic delete <name>` and run `make topics` again.

== In production

[.production-note]
Use replication factor 3 and size partitions for peak throughput and for the parallelism of the largest consumer group, not for a laptop. See the Brokers and replication and Partitions rows in xref:index.adoc#_production_considerations[Production considerations].
