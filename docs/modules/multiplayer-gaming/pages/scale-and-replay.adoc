== Why

The burst shows what lag is: the distance between the newest record and the last one a group committed. It is the one number to alert on for any consumer, and the dashboard reads it from the same source `rpk group describe` does.

Scaling shows how consumer groups distribute work. Nobody told the new instances which partitions to take; joining the group is enough. The coordinator ran a rebalance and each member got two of six partitions. The ceiling is six instances, which is why xref:create-topics.adoc[] chose six partitions. A new owner does not start from zero: its first record on a partition arrives with a committed offset, so it loads that partition's players from `game.leaderboard`, the totals as of the offsets written into each entry, and continues from there. Three writers publishing totals for disjoint sets of players never contend.

The replay is the reason to build on a log at all. The board on `game.leaderboard` was never the source of truth; `game.player-events` is. Seeking the group to the start makes every instance recompute every total from the first record and publish each one again. The compacted topic absorbs thousands of superseded entries and converges, within a minute or two, back to one record per player, with the same scores it held before. The same move fixes a bug in the leaderboard logic (deploy the fix, seek, replay), bootstraps a new consumer that needs history, or rebuilds a view that was lost.

== Why Redpanda

Consumer group offsets are the consumer's, not the broker's, and `rpk group seek` edits them. Retention on `game.player-events` (7 days here, longer with Tiered Storage) decides how far back a replay can go. Compaction on `game.leaderboard` means the replay costs nothing lasting: the extra records are gone after the next compaction pass. Cooperative rebalancing moves only the partitions that need to move, so two instances keep working while the third joins. See xref:streaming:reference:rpk/rpk-group/rpk-group-seek.adoc[], xref:streaming:develop:consume-data/consumer-offsets.adoc[], and xref:streaming:manage:cluster-maintenance/compaction-settings.adoc[].

== What happens inside

During the burst the simulator's ticker fires 2000 times a second and the producer batches records per partition; the leaderboard applies them as fast as it can publish, so its committed offsets fall behind the high watermarks and the lag the dashboard reads rises. When the burst ends the group drains the difference.

When the second and third instances join, the coordinator triggers a rebalance with the cooperative-sticky protocol. Partitions are revoked from the first instance in a first round and assigned to the newcomers in a second. The first instance blocks the revocation until the batch it holds is published and committed (`BlockRebalanceOnPoll`), then drops the state of the players on the revoked partitions. Each newcomer's first record on a partition has an offset above 0, so `seed` takes a snapshot of `game.leaderboard`, keeps the entries whose `source_partition` is that partition, and resumes with those totals. Any record at or below an entry's `source_offset` is a duplicate and is skipped.

`rpk group seek leaderboard --to start` writes offset 0 for each of the six partitions into `__consumer_offsets` on behalf of the group. When the instances start again their first record on every partition is at offset 0, so `seed` loads nothing and logs `rebuilding its totals from scratch`. They apply every `score_changed` again in the original per-partition order and publish every intermediate total; the dashboard's map is overwritten entry by entry, which is the dip you saw. When the lag reaches 0 the last entry published for each player is the same total as before, because the log has not changed. `before.txt` and `after.txt` are identical. The poison record and the burst are replayed too, and are handled the same way.

Meanwhile `game.leaderboard` has thousands more records than players. Run `docker compose exec -T rpk rpk topic consume game.leaderboard -o :end -f '%k\n' | wc -l` a few times over the next minutes and watch it fall back toward 24: each partition rolls its segment after 60 seconds, and the compaction pass rewrites the closed segments with one record per key.

== In production

[.production-note]
Scale consumer groups on lag, keep instance counts at or below the partition count, and use Tiered Storage so the replay window is a retention setting rather than a disk size. Give `game.leaderboard` a `segment.ms` and dirty ratio suited to its write rate; the 60-second segments here exist so you can watch compaction happen. See the Consumer scaling and Data retention rows in xref:index.adoc#_production_considerations[Production considerations].
