= Produce player events
:page-layout: solution-step
:description: Let the deterministic simulator produce exactly 3000 events with an idempotent, acks=all producer, then read them back in Console and with rpk.
:page-solution-step-duration: 5

The simulator is already producing. In this step you let it run to its cap of exactly 3000 events, read the records back in Console and with `rpk`, and look at the producer settings that make the counts exact and the retries safe.

== What you do

. Wait for the simulator to stop at `SIM_EVENTS_MAX`:
+
[,bash]
----
make seed
----
+
`make seed` runs `make topics` and `make schemas` first (both are no-ops now), then polls the simulator until its state is `capped` and prints the counters. At 100 events per second this takes about 30 seconds.

. Open Console at http://localhost:8080/topics/game.player-events and select a record. Console shows the Protobuf payload as JSON, with `scoreChanged`, `itemAcquired`, or `playerJoined` as the populated `oneof` case and the `event_type` header alongside.

. Read one partition with `rpk`, decoding through Schema Registry:
+
[,bash]
----
docker compose exec -T rpk rpk topic consume game.player-events -p 1 -o start -n 2 \
  --use-schema-registry=value
----

== Why

Three settings on the producer carry the design. Idempotence gives every partition a producer ID and a sequence number, so a retried batch after a timeout is deduplicated by the broker and a `score_changed` is never applied twice on the log. `acks=all` waits for the full in-sync replica set before the send is acknowledged; with one replica it changes nothing here, with three it is the difference between a durable score and a lost one. The sticky key partitioner hashes the key like the Java client does, so `player_id` maps to the same partition from any client language.

The generator is deterministic on purpose. It seeds a random source from `SIM_SEED`, keeps its own simulated clock (200 simulated milliseconds per event), and returns exactly one event per call, queuing the several events of a match start or match end so a hard stop at 3000 never leaves half a match on the log. Same seed, same 3000 records, same timestamps, which is what lets `scripts/verify.sh` assert exact numbers and lets you compare a replay with the original in xref:scale-and-replay.adoc[].

== Why Redpanda

Idempotent producers are on by default in Redpanda and in franz-go, and they cost nothing measurable. The `event_type` record header lets Redpanda Connect route without decoding the payload first (xref:persist-match-history.adoc[]), and the Confluent wire format the `sr` serde writes is what Console and Connect decode. See xref:streaming:develop:produce-data/idempotent-producers.adoc[] and xref:streaming:develop:produce-data/configure-producers.adoc[].

== What happens inside

For each event the simulator serializes the Protobuf message, prefixes the schema ID header, hashes the key to pick a partition, and appends the record to a per-partition batch. Batches are sent after 5 ms of lingering, compressed with Snappy, and the broker drops any retried batch it has already appended by checking the producer's sequence number (xref:streaming:develop:produce-data/idempotent-producers.adoc[]). The high watermark of each partition advances by the number of records in the batch; the sum across the six partitions of `game.player-events` plus the three of `game.match-events` is 3000 once the simulator reports `capped`.

The three consumers have been reading since the first record arrived. The next three steps look at each in turn.

== Verify

Run:

[,bash]
----
curl -s http://localhost:8090/stats | grep -E '"state"|"acked_total"'
----

Expected output:

[.solution-verify]
[,text]
----
  "state": "capped",
  "acked_total": 3000,
----

If the state is still `producing`, wait and repeat; if it is `waiting_for_schema`, `make schemas` did not complete. If `acked_total` is lower than `generated_total`, the simulator is still receiving acknowledgements or logged produce errors; `docker compose logs simulator` shows them.

== In production

[.production-note]
Keep idempotence on and `acks=all`; add TLS and SASL to the client options, and scope its ACLs to `WRITE` on the two topics. See the Idempotency and delivery row in xref:index.adoc#_production_considerations[Production considerations].
