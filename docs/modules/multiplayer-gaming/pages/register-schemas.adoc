= Register the schemas
:page-layout: solution-step
:description: Register the GameEvent Protobuf schema for each topic, set BACKWARD compatibility, evolve it to a second version, and watch Schema Registry refuse a breaking change.
:page-solution-step-duration: 5

You register the `GameEvent` Protobuf schema under one subject per topic, set the compatibility level, then register a second version that adds a field. Finally you ask Schema Registry to check a change that would break consumers, and it refuses. When this step ends, the simulator starts producing on its own.

== What you do

. Register version 1 for each of the three value subjects, set `BACKWARD` compatibility, then register version 2. `make schemas` does all of it and is safe to repeat:
+
[,bash]
----
make schemas
----

. Compare the two versions. Version 2 adds one optional field, `region`, to the envelope:

[,protobuf]
----
include::example$proto/game_events.proto[tags=envelope]
----

. Ask Schema Registry whether a breaking change would be accepted. `proto/history/game_events.breaking.proto` changes `player_id` from `string` to `int64`:
+
[,bash]
----
docker compose exec -T rpk rpk registry schema check-compatibility game.player-events-value \
  --schema /proto/history/game_events.breaking.proto --type protobuf --schema-version latest
----
+
The first lines of the output:
+
[,text]
----
Schema is not compatible.
{errorType:"FIELD_SCALAR_KIND_CHANGED", description:"The kind of a SCALAR field at path '#/GameEvent/2' in the new schema does not match its kind in the old schema"}
----

. Watch the simulator wake up:
+
[,bash]
----
docker compose logs simulator --tail 5
----
+
It logs `game.player-events-value -> schema id 2`, the same for `game.match-events-value`, and starts producing.

== Why

The schema is the contract between the game servers and every consumer, and it will change: this step already changes it once. Three things make that safe here. The schema is registered under `<topic>-value`, the default subject naming strategy, so Console, Redpanda Connect, and any client that reads the topic find it without configuration. Compatibility is `BACKWARD`, so a new version is accepted only if a consumer compiled against it can still read every record written under the previous version, which is the direction you need when you upgrade consumers before producers. And the producers look the schema up instead of registering it, so a service built against an unregistered schema waits and logs, rather than pushing a new version into the registry at deploy time.

== Why Redpanda

Schema Registry is part of the broker, stores its state in the `_schemas` topic you saw in step 2, and speaks the Confluent-compatible API, so franz-go's `sr` package, Redpanda Connect's `schema_registry_decode`, and Console all work against it unchanged. Protobuf compatibility checking understands field kinds, `oneof` moves, and removed fields. See xref:streaming:manage:schema-reg/schema-reg-overview.adoc[] and xref:streaming:reference:rpk/rpk-registry/rpk-registry-schema-create.adoc[].

== What happens inside

`rpk registry schema create` posts the `.proto` text to `/subjects/game.player-events-value/versions`. Schema Registry parses it, checks it against the subject's compatibility rule, assigns a global schema ID (1 for version 1, 2 for version 2), and stores it in `_schemas`. Because the text is identical for the three subjects, they share the IDs. Repeating the command with the same text returns the existing ID, which is why `make schemas` is idempotent.

== Verify

Run:

[,bash]
----
docker compose exec -T rpk rpk registry schema list game.player-events-value
----

Expected output:

[.solution-verify]
[,text]
----
CONTEXT  SUBJECT                   VERSION  ID    TYPE      ERROR
default  game.player-events-value  1        1     PROTOBUF
default  game.player-events-value  2        2     PROTOBUF
----

If version 2 is missing, the compatibility check rejected it. `rpk registry compatibility-level get game.player-events-value` should print `BACKWARD`; `make schemas` sets it before registering version 2. If the IDs differ from `1` and `2`, other schemas were registered first; nothing depends on the exact numbers.

== In production

[.production-note]
Turn on broker-side schema ID validation so a producer cannot write a record whose schema ID is not registered under the topic's subject, and keep producers looking schemas up rather than auto-registering. See the Schema validation row in xref:index.adoc#_production_considerations[Production considerations].
