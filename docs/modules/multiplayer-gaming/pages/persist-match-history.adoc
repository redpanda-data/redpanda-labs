= Persist the match history
:page-layout: solution-step
:description: Land both topics in Postgres with a Redpanda Connect pipeline that decodes through Schema Registry, flattens the oneof, inserts idempotently, and dead-letters what it cannot decode.
:page-solution-step-duration: 6

Redpanda Connect has been writing Postgres since the simulator started in xref:produce-player-events.adoc[]. You query the two tables, then produce one deliberately unreadable record and follow it to the dead-letter topic with the error attached. No code is involved: the pipeline is fifty lines of YAML.

== What you do

. Count the finished matches and look at one:
+
[,bash]
----
docker compose exec -T postgres psql -U game -d game \
  -c "SELECT COUNT(*) FROM match_history" \
  -c "SELECT match_id, winner_player_id, duration_seconds, player_ids FROM match_history ORDER BY match_id LIMIT 3"
----

. Check that the sink agrees with the source. Every `game.player-events` record is a row, grouped by type:
+
[,bash]
----
docker compose exec -T postgres psql -U game -d game \
  -c "SELECT event_type, COUNT(*) FROM player_events GROUP BY 1 ORDER BY 1"
----
+
The counts equal `events_by_type` at http://localhost:8090/stats: 761 `item_acquired`, 216 `player_joined`, 192 `player_left`, 1729 `score_changed`.

. Produce a poison record. The simulator writes one record to `game.player-events` whose schema ID, `2147483647`, is registered nowhere:
+
[,bash]
----
curl -s -X POST http://localhost:8090/poison
----

. Find it on the dead-letter topic:
+
[,bash]
----
docker compose exec -T rpk rpk topic consume game.player-events.dlq -o start -n 1
----
+
The record keeps its key `poison`, its `event_type` header, and gains `error`, `kafka_topic`, `kafka_partition`, and `kafka_offset` headers: everything needed to inspect it and replay it after a fix.

== Why

Analysts want match history in a database, and that requirement should cost nothing in code and nothing in latency for the leaderboard. Redpanda Connect meets both: the pipeline is configuration, and its consumer group `connect-history` reads at Postgres speed while the leaderboard group reads at broker speed.

The `mapping` flattens the Protobuf `oneof` into two row shapes, one per table, because a relational table wants columns, not a nested `scoreChanged` object. `match_started` records are dropped (`root = deleted()`): the history table is about finished matches, and the `match_ended` event carries the start time. Both inserts end with `ON CONFLICT DO NOTHING` on the event's natural key, so a redelivered record (Connect is at-least-once, like the Go services) inserts nothing twice. The tables:

The dead-letter path exists because a stream will, eventually, carry a record the pipeline cannot process, and the pipeline should not stop and should not drop it. `try` marks a failed message instead of aborting the batch, `reject_errored` refuses to send marked messages to the database, and `fallback` hands them to the next output with the reason in `@fallback_error`.

== Why Redpanda

The `redpanda` input, `schema_registry_decode`, `sql_insert`, and `fallback` are built-in components that know the Confluent wire format and Schema Registry, so the pipeline needs no schema file and no code. The record header the producer set in xref:produce-player-events.adoc[], `event_type`, is available to Bloblang as `@event_type`, which is how the mapping knows the shape before it reads the payload. See xref:connect:components:processors/schema_registry_decode.adoc[], xref:connect:components:outputs/sql_insert.adoc[], and xref:connect:configuration:error_handling.adoc[].

== What happens inside

For each record the input fetches, `schema_registry_decode` reads the schema ID from the first five bytes, fetches schema 2 from Schema Registry once and caches it, and decodes the Protobuf into JSON using the Protobuf JSON mapping (field names in lowerCamelCase, 64-bit integers as strings; the mapping converts what the tables need). The `switch` output sends `match_ended` rows to `match_history` and every other row to `player_events`, batching 100 rows or 500 ms at a time. The input commits the group's offset after the output acknowledges the batch.

The poison record fails inside `try`: schema `2147483647` does not exist. `reject_errored` refuses it, `fallback` moves to its second output, the small `mapping` copies the error into a header, and the `redpanda` output writes the original bytes to `game.player-events.dlq` under the original key. The Go consumers meet the same record; they log it, count it as `poison_skipped`, and commit past it. Each consumer chooses its own policy, which is the point of keeping them independent.

== Verify

Run:

[,bash]
----
docker compose exec -T postgres psql -U game -d game -tA -c "SELECT COUNT(*) FROM match_history"
----

Expected output:

[.solution-verify]
[,text]
----
48
----

48 is the number of `match_ended` events in the seeded 3000 (`events_by_type` at http://localhost:8090/stats). If the count is lower, the pipeline is behind: `docker compose exec -T rpk rpk group describe connect-history` shows the lag, and `docker compose logs connect` shows Postgres errors. If the dead-letter topic is empty after the poison request, wait a few seconds; the fallback output batches like the primary one.

== In production

[.production-note]
Alert on growth of `game.player-events.dlq`, keep its records long enough to replay them after a fix, and run the pipeline with metrics exported so lag and errors are graphed alongside the brokers'. See the Dead-letter handling and Observability rows in xref:index.adoc#_production_considerations[Production considerations].
