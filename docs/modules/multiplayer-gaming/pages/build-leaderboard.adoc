== Why

A leaderboard is a sorted set, and a score change is an increment, so each `score_changed` becomes two `ZINCRBY` calls: one on `leaderboard:global`, one on `leaderboard:match:<match_id>`. Redis keeps the set ordered; the dashboard reads the top 10 with `ZREVRANGE` and pushes it to the browser over server-sent events every 500 ms, so the page never polls.

The service commits offsets by hand, after the Redis writes of a batch succeed. That order matters. Commit first and a crash between the commit and the write loses score changes for good. Write first and a crash between the write and the commit replays the batch on restart: the same increments applied twice. The service chooses the second failure mode, at-least-once, because a duplicate is visible and fixable and a loss is neither. The fix for the duplicate is a few lines and is already in the code, off by default (see _In production_).

`skipped` on the dashboard counts the records that are not `score_changed` (joins, item pickups, leaves). They are read, ignored, and committed like the rest; a consumer group's offset is per partition, not per event type.

== Why Redpanda

The leaderboard group's offsets are its own. Redpanda Connect and the achievements service read the same partitions at their own pace, and a slow Postgres in step 6 changes nothing here. The lag number on the dashboard comes from the same place `rpk group describe` reads: the difference between the group's committed offset and the partition's high watermark. See xref:streaming:develop:consume-data/consumer-offsets.adoc[].

== What happens inside

On startup the client joins the group `leaderboard`, and the group coordinator assigns it all six partitions because it is the only member. `PollRecords` fetches up to 500 records across those partitions. For each `score_changed` the service pipelines the two `ZINCRBY` calls and an `EXPIRE` on the match key in one round trip to Redis. When the whole batch is applied, `CommitUncommittedOffsets` writes the next offset of every partition it read from into `__consumer_offsets`. A record whose schema ID is not registered under `game.player-events-value` (step 6 produces one) is counted as `poison_skipped` and committed past; the service decides that a record it cannot read should not stop the board.

A second background loop asks the broker for the group's lag every second, which is what the dashboard shows and what step 8 makes visible.

== Verify

Run:

[,bash]
----
curl -s 'http://localhost:3000/api/top?n=3'
----

Expected output (the beginning; the `status` object follows):

[.solution-verify]
[,text]
----
{
  "match": "",
  "top": [
    {
      "rank": 1,
      "player_id": "p014",
      "score": 795
    },
    {
      "rank": 2,
      "player_id": "p024",
      "score": 715
    },
    {
      "rank": 3,
      "player_id": "p021",
      "score": 715
    }
----

These exact scores follow from `SIM_SEED=42` and `SIM_EVENTS_MAX=3000`. Different numbers mean a different seed or cap in `.env`, or a simulator that was bursting (step 8). A `lag` above 0 in `status` that does not fall means Redis is refusing writes; `docker compose logs leaderboard-service` shows the error.
