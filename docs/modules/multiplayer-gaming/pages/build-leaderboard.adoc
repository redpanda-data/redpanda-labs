== Why

A leaderboard is a per-player total, and the consumer that owns a player's partition sees every one of that player's score changes, in order. So the service aggregates where the data already is: it adds each `score_changed` delta to an in-memory total for that player. Nothing else is needed to compute the board.

It then publishes the total, never the delta. A delta is an instruction ("add 15") and applying it twice is a bug. A total is a fact ("p014 has 795") and publishing it twice is harmless. That single choice is what makes the rest of this solution safe: a redelivered batch, a rebalance, or the full replay in xref:scale-and-replay.adoc[] can only ever write the same fact again.

The topic is compacted, so it converges to one record per player: a materialized view of the board, stored in Redpanda, with no database. Any reader that consumes `game.leaderboard` from the start ends up holding the complete board without replaying a single game event. The dashboard is exactly that reader, and it is deliberately thin: a map, a sort, and an HTTP handler. It never decodes a `GameEvent`.

The service commits offsets by hand, after the entries of a batch are acknowledged, and it blocks a rebalance until the batch in hand is committed. A crash between the publish and the commit replays the batch, and because each entry records the source offset it was computed from, the replayed records are recognized and skipped (`duplicates_skipped` in the service's `/healthz`). Publishing totals makes a duplicate harmless; the offset makes it a no-op.

== Why Redpanda

Compaction is a topic property, `cleanup.policy=compact`, and the broker does the rest in the background: it rewrites closed segments so that only the newest record per key survives. That is what lets a topic act as a key-value store that streams. `segment.ms` is set low here (60 seconds) so you can watch it happen; production values are minutes to hours. The `leaderboard` group's offsets are its own, so Redpanda Connect and the achievements service read the same partitions at their own pace, and a slow Postgres in xref:persist-match-history.adoc[] changes nothing here. See xref:streaming:manage:cluster-maintenance/compaction-settings.adoc[] and xref:streaming:develop:consume-data/consumer-offsets.adoc[].

== What happens inside

On startup the client joins the group `leaderboard`, and the group coordinator assigns it all six partitions because it is the only member. `PollRecords` fetches up to 500 records across those partitions. The first record of each partition triggers `seed`:

On a fresh stack every partition starts at offset 0, so the service logs `rebuilding its totals from scratch` six times (five, if one partition received no player) and computes as it reads. For each `score_changed` it updates the total and produces a `LeaderboardEntry` keyed by `player_id`. When the whole batch is applied, `Flush` waits for the broker to acknowledge the entries, `CommitUncommittedOffsets` writes the next offset of every partition into `__consumer_offsets`, and `AllowRebalance` lets a pending rebalance proceed. A record whose schema ID is not registered under `game.player-events-value` (xref:persist-match-history.adoc[] produces one) is counted as `poison_skipped` and committed past; a record the service cannot read should not stop the board.

On `game.leaderboard`, the producer hashes `player_id` to one of three partitions, so each player's entries land in one partition in order, which is all compaction needs to keep the right one. Every minute the active segment of each partition closes; Redpanda's compaction pass, which runs every 10 seconds, rewrites the closed segments and drops the superseded entries. The `rpk` count in step 3 shrinks toward 24.

== In production

[.production-note]
The board on `game.leaderboard` is the source of truth for every reader, and the dashboard's in-memory map is enough to serve a top 10. When you need per-player rank queries at scale ("where is p014?"), serve them from Redis or another key-value store that is itself just one more consumer of `game.leaderboard`, loaded from the start and kept current from the tail. Give the topic a `segment.ms` and `min.cleanable.dirty.ratio` sized for your write rate, and keep publishing absolute totals. See the Idempotency and delivery and Data retention rows in xref:index.adoc#_production_considerations[Production considerations], and xref:streaming:manage:cluster-maintenance/compaction-settings.adoc[].
