= Create the contract
:page-layout: solution-step
:description: Create the four topics with deliberate partition counts and one compaction policy, register the three Avro schemas, and set the compatibility level that makes a provider's later change safe.
:page-solution-step-duration: 6

You create the topics and register the schemas. Together those are the contract: the topics decide how far each consumer can scale and what ordering it can rely on, and the schemas decide what a record means. Nothing in this solution registers a schema at runtime, so this step is what unblocks the feed.

The four topics and the reason for each shape:

[cols="2,1,1,3"]
|===
| Topic | Partitions | Key | Why

| `sports.feed`
| 6
| `fixture_id`
| Everything about one match, in order, on one partition. Six partitions is the ceiling for each consumer group.

| `sports.odds`
| 6
| `market_id`
| Written by the odds engine. Keyed by market, because a market's prices must arrive in order at whatever shows them, and different markets need not be ordered against each other.

| `sports.market-state`
| 3
| `fixture_id`
| Written by the market-state service: each fixture's current state. Compacted, so it converges to one record per fixture and becomes the desk's book rather than a history of it.

| `sports.feed.dlq`
| 1
| original key
| Records the Connect pipeline could not handle. One partition is plenty for something that should stay empty.
|===

== Why

The key on `sports.feed` is the fixture, not the market. Markets belong to a fixture, and a suspension is an event about a market that must never be delivered after the price it suspends. Keying by market would put a fixture's markets on different partitions, and the order between them would then be whatever the network decided. Keying by fixture gives every consumer one ordered stream per match, which is the strongest guarantee any of the three actually needs, and it is what lets the market-state service keep its state in memory rather than in a shared store.

`sports.market-state` is the odd one out. It carries each fixture's current state, and only the newest matters, so its cleanup policy is `compact`: the broker keeps the latest record per key and discards the rest. That turns the topic into the desk's book, which any new consumer can read from the start without replaying the feed.

Registering the schemas is a separate act from creating the topics because it is a separate decision, made by whoever owns the data's shape. The compatibility level is set after the first registration on purpose: the first schema has nothing to be compatible with.

== Why Redpanda

Schema Registry is part of the broker, so the contract lives next to the data and there is no separate service to deploy, secure, or keep in sync. `rpk registry` creates subjects, sets compatibility levels, and checks a candidate schema without a client library, and Console and Redpanda Connect decode records through the same registry with no extra configuration. See xref:streaming:manage:schema-reg/schema-reg-overview.adoc[] and xref:streaming:reference:rpk/rpk-registry/rpk-registry.adoc[].

== What happens inside

`rpk` sends a `CreateTopics` request. The controller creates each partition as a Raft group, assigns leaders, and writes the topic properties to the controller log. From now on every record keyed `fx-epl-2026-0412` lands on the same partition, because the producer hashes the key to choose one. With four fixtures and six partitions the spread is uneven and some partitions stay empty, which is normal for a small key space and visible in xref:ingest-the-feed.adoc[].

Registering a schema returns an ID, and that ID is what goes into every record. The subject `sports.feed-value` now has one version; xref:evolve-the-schema.adoc[] adds the second and leaves both in use.

Within two seconds the feed service finds the schema it has been waiting for, logs the ID it will write under, and starts producing. The three consumers find their topic and join their groups.

== In production

[.production-note]
Size partitions for the busiest day rather than the average one, and switch schema ID validation on so the broker refuses a record whose schema is not registered. See the Partitions and Schema validation rows in xref:index.adoc#_production_considerations[Production considerations].
