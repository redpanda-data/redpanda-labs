= Archive for settlement
:page-layout: solution-step
:description: Land every provider event in Postgres with Redpanda Connect, keyed so a replay cannot double-count, with a dead-letter topic for anything it cannot handle.
:page-solution-step-duration: 5

The third consumer has no code in it. A Redpanda Connect pipeline reads `sports.feed` in the group `feed-archive`, decodes each record through Schema Registry, and inserts it into Postgres. Its job is not to be fast. Its job is to be complete, because a settlement dispute or a regulator's question is answered from this table, months later.

== Why

The insert is `ON CONFLICT (fixture_id, seq) DO NOTHING`, and the key is the provider's, not ours. That is the whole reason the replay in xref:replay-one-consumer.adoc[] is safe: an event's identity is what the provider said it was, so redelivering it inserts nothing, and no offset arithmetic or exactly-once machinery is needed to get there.

The `provider` field is read with a default, which is what lets the same pipeline keep working across the schema change in xref:evolve-the-schema.adoc[]:

[source,yaml]
----
include::example$connect/feed-archive.yaml[tag=pipeline]
----

Nothing is dropped. A record the pipeline cannot decode or insert goes to `sports.feed.dlq` with the original key, the headers, and the error attached, so it can be inspected and replayed after a fix. An archive that silently loses an event is worse than no archive, because it is trusted.

== Why Redpanda

Redpanda Connect is one YAML file and one container: no Kafka Connect cluster, no plugin JARs, no code. The `redpanda` input joins its own consumer group, which is what makes this a third independent reader rather than a tap on someone else's; `schema_registry_decode` turns bytes into JSON by reading the schema ID in each record; and `fallback` with `reject_errored` is the dead-letter pattern without a line of Go. See xref:connect:components:inputs/redpanda.adoc[], xref:connect:components:processors/schema_registry_decode.adoc[] and xref:connect:components:outputs/sql_insert.adoc[].

== What happens inside

The input reads from the earliest offset in the group `feed-archive`, so the pipeline sees the whole feed from the start the first time it runs. Records are batched, 100 at a time or every 500 milliseconds, because an archive wants throughput and does not care about a half second. The odds engine, which does care, is unaffected: it has its own group and its own offsets.
