= Cut over to Redpanda
:page-layout: solution-step
:description: Pause schema replication so the Redpanda registry accepts writes, fail the shadow topics over so they accept records, and produce the next order on Redpanda with the same client.
:page-solution-step-duration: 5

Both halves are on Redpanda and the source is still the writer. You now make Redpanda the writer: pause schema replication, which lifts the write block on the registry, fail the topics over, which promotes them to ordinary topics, and point the client at Redpanda for its next record. Topic failover cannot be undone, so this is the step to rehearse.

== Why

Cut-over is two switches because the link has two tasks. Pausing the registry task stops polling the source and releases the destination context, so new schemas can be registered on Redpanda; that is what your producers need the moment they point at the new registry. Failing the topics over stops fetching from the source and turns the read-only shadow topics into normal topics, so producers can write. The canonical sequence does both together, as one unit, and this step follows it. Doing only one leaves you with a cluster that either accepts schemas but not records or the reverse, and consumers that cannot tell which.

The order of operations in a real cut-over is what protects you from writing to both clusters: stop the producers on Confluent, wait until every topic shows `LAG 0` and `make compare` agrees, pause and fail over, then start the producers against Redpanda. In this walkthrough the producer is you, so the wait is already over.

== Why Redpanda

Failover is a state change on the shadow topics, not a copy: the data is already there, so promoting the three topics is immediate and the new order lands next to the migrated ones with offset `3`. The link stays in place afterwards, with the registry task paused and the topics in `FAILED_OVER`, so `rpk shadow status` still tells the story of what happened. Delete it when you no longer need that record. See xref:streaming:manage:disaster-recovery/shadowing/failover.adoc[], xref:streaming:reference:rpk/rpk-shadow/rpk-shadow-failover.adoc[], and xref:streaming:reference:rpk/rpk-shadow/rpk-shadow-update.adoc[].

With `paused: true` the Schema Registry Shadowing task stops its sync loops and drops its ownership of the default context, so the next `POST /subjects/cutover-test/versions` is checked, assigned ID `8`, and written to Redpanda's `_schemas` like any other registration. `rpk shadow failover --all` asks the Admin API to move every topic of the link from `ACTIVE` through `FAILING_OVER` to `FAILED_OVER`; each topic's replication fetcher stops, and the topic's partitions accept produce requests. `make wait-failover` polls `rpk shadow status --print-topic` until all three report `FAILED_OVER`. If the `POST` still returns `412`, the pause did not apply: `docker compose exec -T rpk rpk shadow describe schema-registry-migration --print-registry` should show `PAUSED true`.

== In production

[.production-note]
Fail a link over as one unit: stop producers, wait for `LAG 0` and a clean `make compare`, pause the registry task and fail the topics over together, then repoint producers and consumers, and never let both clusters accept writes for the same topics. Turn on schema ID validation on the migrated topics afterwards. See the Idempotency and delivery and Schema validation rows in xref:index.adoc#_production_considerations[Production considerations].
