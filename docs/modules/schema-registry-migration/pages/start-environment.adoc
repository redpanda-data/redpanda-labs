= Start the environment
:page-layout: solution-step
:description: Start the Confluent source, the Redpanda shadow cluster with Shadowing enabled, Redpanda Console, and the client with one command, and confirm both registries are empty.
:page-solution-step-duration: 8

You bring up both sides of the migration with one command: a Confluent broker and Confluent Schema Registry as the source, a Redpanda cluster with Shadowing enabled as the destination, Redpanda Console on the Redpanda side, and the Python client that plays the application. Nothing is replicated yet; the source registry is empty.

== Why

A migration rehearsal is only worth something against the real source, so the source here is Confluent Platform itself, not a second Redpanda pretending to be one. The `cp-schema-registry` image has no UI, and that is deliberate: everything you do to the source goes through its REST API, the same way the shadow link reads it.

The client is a separate container because it is the thing that moves. It starts with two environment variables that point at Confluent, `SOURCE_SR_URL` and `SOURCE_BOOTSTRAP_SERVERS`, and in xref:cut-over.adoc[] you point the same code at Redpanda by overriding them. If the client needed a code change to cut over, the migration would not be finished.

== Why Redpanda

Shadowing is part of the broker: `enable_shadow_linking=true` is the only configuration, and the link you create in xref:create-shadow-link.adoc[] runs inside the destination cluster with no separate connector process or replication tooling to deploy. The destination's Schema Registry is built into the same binary, so the registry that receives the subjects is already running. See xref:streaming:manage:disaster-recovery/shadowing/overview.adoc[].

== What happens inside

Confluent's broker starts in KRaft mode as one combined broker and controller and reports healthy when its API answers; the Confluent Schema Registry waits for it and then serves an empty registry on port 8081 inside the network (`38081` on the host). Redpanda starts in `dev-container` mode with `--memory 1G`, advertises `redpanda:9092` inside the compose network and `localhost:29092` outside it, and reports `Healthy: true` once its single Raft group has a leader. Console connects to Redpanda's Kafka API, Schema Registry, and Admin API. The `rpk` helper container has the link configuration mounted at `/config` for the next steps, and the client image is built from `client/Dockerfile` with pinned Python dependencies plus `curl` and `jq`.

If `make up` stops with a container marked `unhealthy`, run `docker compose logs <service>`. The usual causes are Docker having less than 4 GB of memory available (the Confluent broker fails to start its JVM, or Redpanda fails to allocate `--memory 1G`) and one of the host ports already in use (move it with the matching `*_PORT` variable in `.env`, then substitute it in the commands that follow). If `enable_shadow_linking` prints `false`, you started from an older volume; `make clean` and start again.

== In production

[.production-note]
The two clusters are deployed and secured separately, and the link connects to the source over TLS with credentials scoped to reading topics and the registry. See the Brokers and replication and Security rows in xref:index.adoc#_production_considerations[Production considerations].
