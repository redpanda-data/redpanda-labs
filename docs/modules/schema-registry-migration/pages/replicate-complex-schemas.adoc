:page-layout: solution-step

You now register the things that make a registry migration hard: a schema that references another subject, a compatibility override on that subject, and subjects of the two other schema types. Then you watch the next full sync bring every one of them across and look at the result in Redpanda Console.

== Why

References are the part of a registry that a naive copy gets wrong. `shipping-value` is only parseable once `address-value` exists, and it must exist under the same subject name and version, or the reference points at nothing. A compatibility override has to travel with its subject, or the destination silently applies the global default to a subject the source guarded with `FULL_TRANSITIVE`. And a registry that only understood Avro would drop a third of a typical Confluent deployment. This step puts one of each on the source so `make compare` can prove they all arrived. == Why Redpanda

Redpanda's Schema Registry supports Avro, JSON Schema, and Protobuf, schema references, and per-subject compatibility levels, and the API-mode link imports referenced schemas in dependency order, so `address-value` is always present before `shipping-value` is registered on the destination. Console reads the replicated registry through its normal API and shows references and compatibility in the subject view. See xref:streaming:manage:schema-reg/schema-reg-overview.adoc[] and xref:streaming:console:ui/schema-reg.adoc[].

== What happens inside

The tail sync notices changed subjects every 10 seconds, but a subject that did not exist on the source at the last full sync is picked up by the next full sync, which lists every subject in the selected contexts and imports what is missing. For `shipping-value` the task fetches version 1, sees its `references` list, makes sure `address-value` version 1 exists on the destination first, then registers `shipping-value` with the same reference and the same global ID `5`. The `FULL_TRANSITIVE` setting is a separate `/config/shipping-value` object and is counted under `COMPATIBILITY CONFIGS CHANGED` in the link status. The JSON Schema and Protobuf subjects are validated by Redpanda's parsers for those types before import; with `unsupported_schema_feature_policy: REMOVE`, a Confluent rule set or metadata block on any of them would be stripped and counted under `UNSUPPORTED FEATURES REMOVED` instead of failing the sync.

A `404` means the full sync has not run since you registered the subject; wait 20 seconds and try again. If `make compare` reports a `MISMATCH` on `shipping-value` only, check `rpk shadow status` for an import error on `address-value`, the subject it depends on.

== In production

[.production-note]
Count on references and overrides being the subjects that surface problems: run the rehearsal with `unsupported_schema_feature_policy: FAIL`, read the `ERRORS` and `UNSUPPORTED FEATURES REMOVED` counters, and decide per subject before you switch to `REMOVE`. See the Dead-letter handling row in xref:index.adoc#_production_considerations[Production considerations] and xref:streaming:manage:disaster-recovery/shadowing/migrate-schemas-confluent.adoc#choose-a-validation-policy[].
