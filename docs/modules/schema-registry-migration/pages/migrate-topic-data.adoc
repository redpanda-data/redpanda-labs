== Why

The migration only works if the bytes in a record and the registry that decodes them agree on what an ID means. The client makes that explicit by framing records itself instead of using a serializer library, so the contract is visible: a `0x00` magic byte, the schema ID as four big-endian bytes, then the Avro body.

The three consume runs are the same code with different endpoints, and together they are the argument for the whole design: the second run proves the registry migrated correctly (a consumer that only knows Redpanda's registry decodes Confluent's records), and the third proves the data migrated too.

== Why Redpanda

The link's topic sync creates each shadow topic with the source's partition count and properties and replicates from the earliest offset because the file says `start_at_earliest`, so the whole history moves, not just new records. The client joins no consumer group: it assigns every partition itself, reads from the first offset to the high watermark, and commits nothing, so every run reads the whole topic on either cluster and depends on nothing but the records. See xref:streaming:manage:disaster-recovery/shadowing/setup.adoc[] for the topic sync options and xref:streaming:manage:disaster-recovery/shadowing/monitor.adoc[] for the status you printed.

== What happens inside

The producer looks up `orders-value/versions/latest` and gets ID `3` (version 2), `customers-value` gets `2`, and `shipping-value` gets `5` along with its reference, which the client resolves by fetching `address-value` version 1 so `fastavro` knows the `Address` type. The Confluent broker auto-creates the three topics on the first produce, one partition each. Within `interval` (10 seconds) the link's source topic sync sees three topics that match its `INCLUDE` filters, creates read-only shadow topics with the same names on Redpanda, copies the listed properties, and starts fetching from offset 0. The status shows `SRC-HWM`, `DST-HWM`, and `LAG` per partition.

The consumer does the lookup in reverse. For every record it reads the ID out of the first five bytes and calls `/schemas/ids/<id>` on whichever registry `SR_URL` names:

Six records, three schemas, all from `redpanda`. This is the migrated state: data and the schemas that decode it both live on Redpanda, with the source still running. If the consumer prints `0 record(s)`, the shadow topics are not there yet (`make wait-topics` waits for them). If it fails on `/schemas/ids/<id>`, the schema for that ID has not replicated; records can arrive before their schema, so check `make compare` first.

== In production

[.production-note]
Add `consumer_offset_sync_options` so consumer groups continue from their committed offsets on Redpanda instead of re-reading history, use prefix or regex topic filters, and expect records to arrive up to `tail_interval` before the schemas they reference. See the Consumer scaling and Data retention rows in xref:index.adoc#_production_considerations[Production considerations].
