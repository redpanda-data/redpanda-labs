== Why

Two databases, one table, because the question the analysts ask is about orders, not about which database the orders happen to live in. The `source` column is what makes that safe: it is set to a literal in each pipeline's mapping, so a query can separate the two whenever it needs to, and the reconstruction query in xref:query-with-spark.adoc[] partitions by `source` and `order_id` rather than `order_id` alone, because both databases number their orders from 1.

Everything else about this step is the same as xref:capture-postgres-changes.adoc[], which is the point worth taking away: the shape of the pipeline, the topic, the schema, and the table do not change when the source database does.

== Why Redpanda

One output, one topic, one table, two inputs. There is nothing to reconcile: the second pipeline writes to the topic the first one writes to, and the broker's translation task does not care how many producers there are. Adding a third database is a third pipeline file. See xref:connect:components:inputs/mysql_cdc.adoc[].

== What happens inside

`mysql_cdc` works differently from `postgres_cdc` in one way that matters. Postgres holds the pipeline's position for it, in the replication slot, on the database server. MySQL has no server-side cursor for a binary log reader, so the pipeline has to remember its own position, which is why the input requires a `checkpoint_cache`:

[source,yaml]
----
include::example$connect/mysql-cdc.yaml[tags=cache]
----

A `memory` cache is fine on a laptop and wrong in production: the position is lost when the container restarts, so the pipeline takes a fresh snapshot and writes every row again. Point it at a durable cache resource instead.

The snapshot itself is heavier than Postgres's. The input runs `FLUSH TABLES WITH READ LOCK` to get a consistent binary log coordinate, reads the primary keys, then reads the rows in batches. The lock is brief but it is a global lock, so a snapshot of a large production table is a change to schedule, not a thing to do at noon.

If the MySQL rows do not arrive, `make cdc-logs` shows the pipeline's output: an access denied message means the replication grants in `mysql/init.sql` did not run, which happens on a reused volume, so `make clean` and start again. A message about the binary log means MySQL started without `--log-bin`.

== In production

[.production-note]
Replace the memory cache with a durable cache resource, or the pipeline re-snapshots the whole table on every restart, and schedule the first snapshot around the global read lock it takes. See the Security and Idempotency rows in xref:index.adoc#_production_considerations[Production considerations].
