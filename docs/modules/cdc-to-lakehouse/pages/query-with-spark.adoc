== Why

The table is a change log, not a copy of the source table, and that is deliberate. A lakehouse table that mirrored current state would have to support row-level updates and deletes, which means a merge job, a schedule, and a window during which the table disagrees with the database. An append-only change log has none of that: Redpanda writes new Parquet files and never rewrites old ones, and the reader decides what "now" means.

The cost is that current state is a query. The one in this step is the standard shape: number the changes per row newest first, keep the first, and drop the rows whose newest change is a delete.

== Why Redpanda

Nothing in this step talks to Redpanda. Spark asks the REST catalog for `lakehouse.redpanda.cdc_orders`, gets a metadata pointer, and reads Parquet files straight out of MinIO, exactly as it would for a table some batch job had written. That is the whole argument for Iceberg topics: the streaming system's output is a table in the format every query engine already reads, so the analysts need no access to the broker and no knowledge that Redpanda exists. See xref:streaming:manage:iceberg/query-iceberg-topics.adoc[].

== What happens inside

Redpanda created the table when the first record was translated. The name is `<catalog>.<namespace>.<topic>`: the catalog is whatever the query engine calls its connection (`lakehouse` here, from `spark/spark-defaults.conf`), the namespace is `redpanda`, which is Redpanda's default and is set per cluster with `iceberg_default_catalog_namespace`, and the table takes the topic's name. That is why the topic is `cdc_orders` and not `cdc.orders`: the table name inherits the dot, and a dotted table name has to be quoted in every query.

Each translation cycle writes one or more Parquet data files under `s3://redpanda/redpanda/cdc_orders/data/` and commits a snapshot to the catalog that lists them. Spark's Iceberg catalog is configured with `cache-enabled false`, so every query re-reads the current snapshot rather than serving a cached table state; with caching on, a query run seconds after a change can miss it.

The `redpanda` struct column is worth knowing about. Redpanda adds it to every Iceberg table it writes, whatever the mode, and it carries the record's Kafka coordinates: key, timestamp, partition, and offset. It is the join key back to the topic when a row in the table needs explaining.

If the query fails with a table not found error, the table has not been created yet: `make wait-lakehouse ROWS=8` and try again, and if it still fails, `make dlq` to see whether the records failed to translate instead. If Spark reports a connection error to `minio` or `catalog`, one of those containers is unhealthy.

== In production

[.production-note]
Point the engines you already have at the same catalog rather than adding Spark for this, and let a downstream job fold the change log into a current-state table on the schedule the analysts need.
