== Why

Two decisions in this step are the ones worth arguing about.

The first is the Iceberg mode. `value_schema_id_prefix` is the mode most examples use, and it requires every producer to frame its records in the Schema Registry wire format: a magic byte, then the schema's id, then the payload. That is correct when many producers write many schema versions to one topic. Here one pipeline writes one shape, and `value_schema_latest` lets it write plain JSON while Redpanda resolves the schema from the subject. The cost is that the mode trusts you to keep the pipeline and the schema in step, which is why schema ID validation is a Production considerations row.

The second is doing this before the capture pipeline exists. It is tempting to start the pipeline first and see the events flowing, then turn on Iceberg. That produces a table that silently misses the snapshot, because translation starts where the property was set, not at the beginning of the log.

== Why Redpanda

The table is a topic property. There is no connector to install, no table to create by hand, no `CREATE TABLE` to keep in step with the schema, and no compaction job: Redpanda lays the table out from the registered schema and maintains it. See xref:streaming:manage:iceberg/about-iceberg-topics.adoc[] and xref:streaming:manage:iceberg/specify-iceberg-schema.adoc[].

== What happens inside

Setting `redpanda.iceberg.mode` does not create anything yet. The table appears in the catalog when the first record is translated, which is why `make query-tables` finds nothing at the end of this step until the next one runs. What the property does is tell the partition leader to run a translation task: read the partition log from the point the property was set, deserialize each record value against the latest schema for `cdc_orders-value`, buffer rows, write Parquet data files into `s3://redpanda/redpanda/cdc_orders/data/`, and commit a new table snapshot to the REST catalog.

Two cluster properties from xref:start-environment.adoc[] control the timing, and both are turned down here so that a change is queryable in seconds rather than minutes: `iceberg_target_lag_ms` is how far behind the topic the table is allowed to fall, and `iceberg_catalog_commit_interval_ms` is how often the leader commits a new snapshot. Production leaves both at their defaults, because every commit is a metadata write and every flush is a new Parquet file, and small files are the thing lakehouses are worst at.

The schema is cached, not read per record. `iceberg_latest_schema_cache_ttl_ms` defaults to five minutes, so in `value_schema_latest` mode a schema you register now can take that long to take effect on a topic that is already translating. Registering it before the first record, as you do here, avoids the question.

The `redpanda` namespace holds no tables yet, and that is the correct answer at this point: the table is created by the first translated record. If `make topic` fails with a topic already exists error, you have run `make seed` already; move on. If `make schema` fails, check that the file you registered is valid JSON Schema draft-07 with a `$schema` keyword, which is a hard requirement.

== In production

[.production-note]
Leave `iceberg_target_lag_ms` and `iceberg_catalog_commit_interval_ms` at their defaults, and enable schema ID validation on the topic so a drifting producer is rejected rather than filling the dead-letter table. See the Schema validation row in xref:index.adoc#_production_considerations[Production considerations] and xref:streaming:manage:iceberg/iceberg-performance-tuning.adoc[].
