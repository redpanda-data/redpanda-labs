A Kafka cluster carries the order flow of a shop: producers write around the clock, a consumer group processes every order, and Schema Registry holds the contracts. Moving that to Redpanda cannot mean stopping producers, replaying history by hand, or losing where each consumer left off.

You run two secured clusters side by side, keep the legacy application writing, and let Redpanda Migrator copy topics, records, schemas, and consumer group offsets continuously. You finish with the consumer running against Redpanda from exactly the offset it had on Kafka, and one script that proves both clusters agree.

After completing this solution, you will be able to:

* [ ] Run Redpanda Migrator as a Redpanda Connect pipeline between two SASL-secured clusters with a least-privilege user on each side
* [ ] Show that migrated topics keep their partition counts, cleanup policies, and retention, and that every record arrives with its timestamp
* [ ] Migrate schemas with their original IDs so that records already on the wire decode on the new cluster, including schemas registered mid-migration
* [ ] Read migration lag from the migrator's metrics and know when the target has caught up
* [ ] Cut a consumer group over to Redpanda from translated offsets, then return the target Schema Registry to normal operation
* [ ] Prove the migration with exact assertions: partitions, configurations, high watermarks, schema IDs, committed offsets

== What you build

Two single-broker Redpanda clusters, both with SASL/SCRAM authentication and ACLs from the first boot. The `source` stands in for the Kafka cluster you are leaving; the migrator speaks the Kafka protocol to it and never notices the difference. A legacy application (a producer and the `orders-service` consumer group, both Redpanda Connect pipelines) works against the source the whole time. Redpanda Migrator copies everything to the `target`, and at the end you move the consumer.

* *`source`*: four `shop.*` topics with different partition counts and cleanup policies, four Avro subjects in Schema Registry, the `orders-service` consumer group.
* *`producer`*: writes one Avro record every 20 ms to the four topics, encoded through the source Schema Registry.
* *`orders-consumer`*: consumer group `orders-service` on `shop.orders`, committing offsets every second. The same pipeline file later runs against the target.
* *`migrator`*: the `redpanda_migrator` input and output, authenticated as the `migrator` user with read-only ACLs on the source and write ACLs on the target only for `shop.*`.
* *`target`*: receives the topics with their configurations, every record with its timestamp and schema ID, every schema with its ID, and the translated offsets of `orders-service`.
* *Redpanda Console*, one per cluster, signed in as the superuser.

== Architecture

image::architecture.svg[Architecture: a producer and the orders-service consumer work against the source cluster; Redpanda Migrator reads the four shop topics, the source Schema Registry, and the group's offsets, and writes the same topics, records, schemas, and translated offsets to the target Redpanda cluster; at the cutover the consumer moves to the target]

Left to right: the producer looks up each topic's schema in the source Schema Registry and writes Avro records to the four `shop.*` topics; the `orders-service` group consumes `shop.orders` and commits offsets to `__consumer_offsets`. Redpanda Migrator reads the topics through the Kafka API as the `migrator` user, reads the registry over HTTP with the same user, and periodically reads the committed offsets of every consumer group on those topics. On the target it creates each topic with the source's partition count and configuration, produces every record with its original key, headers, timestamp, and schema ID, registers every schema version under its original ID (which is why the target registry runs in `IMPORT` mode until the cutover), and commits the translated offsets for `orders-service`. At the cutover the consumer stops on the source, the migrator's next sync brings the target's offsets level with the source's, and the same consumer starts on the target and continues from there.

=== Why Redpanda

* *Redpanda Migrator moves the whole state of a cluster, not only its records.* Topics with their configurations, schemas with their IDs, and consumer group offsets travel in one pipeline, which is the difference between copying data and migrating a system. xref:connect:cookbooks:redpanda_migrator.adoc[]
* *Continuous replication makes the cutover a decision, not an outage.* The migrator keeps the target level with the source while producers keep writing; you choose the moment to move each consumer and can move them one at a time. xref:connect:components:outputs/redpanda_migrator.adoc[]
* *Schema IDs are preserved.* Every record carries its schema ID in its first five bytes. Because the target registry gets the same IDs, records copied yesterday and records produced tomorrow decode with the same registry lookup, and no consumer needs a mapping table. xref:streaming:manage:schema-reg/schema-reg-overview.adoc[]
* *Consumer group offsets are translated, not guessed.* The migrator maps each committed offset through the record's timestamp to the matching position on the target, so a consumer resumes where it stopped instead of from the beginning or the end. xref:streaming:develop:consume-data/consumer-offsets.adoc[]
* *Least privilege is a few ACLs.* The migrator user can read the source and write only `shop.*` on the target; `rpk security acl` expresses that in seven commands. xref:streaming:manage:security/authorization/acl.adoc[]
* *One binary.* Each cluster is one container with the Kafka API, Schema Registry, and the Admin API built in, so a full two-cluster migration lab fits on a laptop. xref:streaming:get-started:intro-to-events.adoc[]

== Prerequisites

* Docker Engine 24 or later with Docker Compose v2, 4 CPUs and 6 GB RAM available to Docker (two brokers at 1 GB each, two Consoles, four Redpanda Connect pipelines)
* `curl` and `make` on the host (every `rpk` command runs inside a container)
* Free host ports `8280`, `8281`, `4295`, `48081`, `49092`, `49644`, `58081`, `59092`, and `59644`, or different ones set with the `*_PORT` variables in `.env`
* Approximately {page-solution-duration} minutes

== Production considerations

This solution runs two single-broker clusters with demo credentials so that it starts in a minute. Before you reuse the design for a real migration, work through this table.

[cols="1,2,2"]
|===
| Area | In this solution | In production

| Brokers and replication
| One broker per cluster, replication factor 1 on both sides; the migrator copies the source's replication factor.
| Three or more brokers on the target, and `topic_replication_factor: 3` on the `redpanda_migrator` output so migrated topics get the target's standard even when the source used less. xref:streaming:deploy:redpanda/manual/production/production-deployment.adoc[], xref:connect:components:outputs/redpanda_migrator.adoc[]

| Security
| SASL/SCRAM with plaintext listeners; superuser credentials for the application and Console; a least-privilege `migrator` user on both clusters; Schema Registry behind HTTP basic auth.
| TLS on every listener and on Schema Registry, one credential per application, the migrator's ACLs exactly as in xref:grant-migrator-access.adoc[] plus `sync_topic_acls` if ACLs move too, and Schema Registry authorization so the registry grants are as narrow as the Kafka ones. xref:streaming:manage:security/encryption.adoc[], xref:streaming:manage:security/authentication.adoc[], xref:streaming:manage:security/authorization/acl.adoc[], xref:streaming:manage:schema-reg/schema-reg-authorization.adoc[]

| Partitions
| Four topics with 12, 6, 8, and 3 partitions; the migrator recreates them with the same counts.
| Keep partition counts identical during the migration: offset translation needs matching counts. Resize on the target after every consumer has moved. xref:streaming:develop:manage-topics/index.adoc[]

| Schema validation
| Schemas registered on the source; the target registry in `IMPORT` mode until the cutover so IDs are preserved; no broker-side validation.
| Migrate with `IMPORT` mode and preserved IDs, return to `READWRITE` as the last step, then enable schema ID validation on the migrated topics. xref:streaming:manage:schema-reg/schema-id-validation.adoc[]

| Consumer scaling
| One consumer instance in `orders-service`, moved by hand in xref:finish-cutover.adoc[].
| Move consumer groups one at a time, each after its own `wait-offsets`, and keep the migrator running until the last producer has switched. xref:streaming:develop:consume-data/consumer-offsets.adoc[]

| Data retention
| The topics keep their source retention (7 days, 1 hour, compaction) on the target.
| Check that the target's retention covers the migration window plus the consumer's expected backlog; a compacted source topic arrives already compacted. xref:streaming:manage:cluster-maintenance/compaction-settings.adoc[]

| Idempotency and delivery
| Records are 20 ms apart, so timestamp-based offset translation lands on the exact record; the cutover step proves it.
| Timestamps are not unique in general, so a translated offset can be a few records early: consumers must tolerate at-least-once delivery across the cutover. The migrator never moves a target offset backwards. xref:connect:components:outputs/redpanda_migrator.adoc[]

| Dead-letter handling
| None: a record the migrator cannot write is retried, and the pipeline stops on a permanent error.
| Alert on `output_error` and on a rising `redpanda_lag`, and keep the source until the target has been verified. xref:connect:configuration:error_handling.adoc[]

| Observability
| `make lag` reads the migrator's Prometheus endpoint; Console on both clusters.
| Scrape the migrator's `/metrics` (`redpanda_lag`, the `redpanda_migrator_*` counters) and both clusters into your monitoring, and alert on lag and on offset commit errors. xref:connect:guides:monitoring.adoc[], xref:streaming:manage:monitoring.adoc[]

| Disaster recovery
| None.
| After the migration, Shadowing keeps a second Redpanda cluster level with the first, with the same offset and schema replication, for failover. xref:streaming:manage:disaster-recovery/shadowing/overview.adoc[]

| Analytics and lakehouse
| None.
| Once the data lives in Redpanda, Iceberg topics write it to a lakehouse table with no pipeline to run. xref:streaming:manage:iceberg/about-iceberg-topics.adoc[]
|===
