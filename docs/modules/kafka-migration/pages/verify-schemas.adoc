== Why

Schema IDs are the join between records and their definitions. A consumer, Console, or Redpanda Connect reads the five-byte header of a record and asks the registry for that ID. If a migration registers the schemas afresh and the target hands out different IDs, every record copied from the source points at the wrong schema or at none, and every consumer needs a translation table until the old records age out. Preserving the IDs (and, for the same reason, the version numbers) makes the copied history usable on the day of the cutover.

Continuous schema sync matters because migrations take days and teams do not stop shipping. A schema registered on the source after the migrator started must reach the target before a record that uses it does; with `interval: 10s` here (five minutes by default), the registry sync runs far more often than schemas change.

== Why Redpanda

The Redpanda Schema Registry implements `IMPORT` mode, so the migrator can register a schema under an explicit ID and version, and `rpk registry` exposes subjects, versions, and mode as commands you can diff between two clusters. `rpk topic consume --use-schema-registry` decodes records the same way an application would, which turns "the schema arrived" into "a copied record decodes". See xref:streaming:manage:schema-reg/schema-reg-overview.adoc[] and xref:streaming:manage:schema-reg/schema-reg-api.adoc[].

== What happens inside

On every sync the output lists the source registry's subjects (including soft-deleted ones, `include_deleted: true`) and, for each subject, every version (`versions: all`). For each version that the target does not have it calls the target registry with the source's ID and version in the request body, which the registry accepts only in `IMPORT` mode; the log line is `schema created with fixed id`. A version that already exists on the target is skipped, so the sync is idempotent. Compatibility levels set per subject carry over as well.

When you registered version 2, the source registry assigned ID 5 (the next free ID after the four originals). Within ten seconds the migrator's sync found the new version and created it on the target with the same ID and version number. The producer keeps writing with schema 1; version 2 is `BACKWARD` compatible, so a consumer reading with either version decodes both.

== In production

[.production-note]
Freeze schema deletions during the migration, keep `versions: all` so consumers pinned to an old version keep working, and plan the `READWRITE` switch as the last step of the cutover. See the Schema validation row in xref:index.adoc#_production_considerations[Production considerations].
