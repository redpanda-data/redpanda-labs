= Start the environment
:page-layout: solution-step
:description: Start the two secured clusters, a Redpanda Console for each, and the rpk helpers with one command, and see that neither cluster accepts a client without credentials.
:page-solution-step-duration: 5

You bring up both clusters with one command: the `source`, which plays the Kafka cluster you are leaving, and the empty `target` Redpanda cluster. Both start with SASL/SCRAM authentication on and a single superuser, the way a real cluster you are allowed to migrate would. Nothing else runs yet: no topics, no application, no migrator.

== Why

A migration starts from a cluster that already has a security posture, so this solution never runs an unauthenticated broker. `RP_BOOTSTRAP_USER` creates the superuser before the broker accepts its first connection, and `enable_sasl` plus `superusers` are set at the same time, so there is no window where the cluster is open and no restart to enable security later. Schema Registry requires HTTP basic auth with the same SCRAM credentials.

Two `rpk` helper containers, one per cluster, carry the connection settings for their side as `RPK_*` variables. Every command in this solution is `docker compose exec -T rpk-source rpk ...` or `docker compose exec -T rpk-target rpk ...`, so which cluster a command talks to is always in the command itself, and no page ever shows a password.

== Why Redpanda

Redpanda serves the Kafka API, Schema Registry, and the Admin API from one binary, so a complete migration lab with two secured clusters is two containers, and `rpk` ships in the same image for the helpers. The `source` is Redpanda too: Redpanda Migrator talks to it as it would to any Kafka cluster, which is the point. See xref:streaming:manage:security/authentication.adoc[].

== What happens inside

Each broker starts in `dev-container` mode with 1 GB of memory, advertises `source:9092` or `target:9092` inside the compose network and `localhost:49092` or `localhost:59092` outside it, creates the SCRAM user from `RP_BOOTSTRAP_USER`, and applies `enable_sasl=true` and `superusers=[admin]` as cluster properties on its first boot. From then on every Kafka connection must authenticate with SASL/SCRAM-SHA-256, and any user who is not a superuser is subject to ACLs. Both Schema Registry listeners are declared with `authentication_method: http_basic`, so `curl` without `-u` gets a `401`.

Console connects to its cluster's broker, Admin API, and Schema Registry with the superuser credentials the compose file passes in as environment variables; the config file carries only the addresses.

If `make up` stops with a container marked `unhealthy`, run `docker compose logs <service>`. The usual causes are Docker having less than 4 GB of memory available (two brokers at `--memory 1G` each) and one of the host ports already in use (move it with the matching `*_PORT` variable in `.env`, then substitute it in the commands that follow). If a helper reports `SASL authentication failed`, the data volume holds a user from an earlier run with a different password: `make clean` and start again.

== In production

[.production-note]
Production clusters add TLS on every listener and give each application its own credential instead of the superuser. The two brokers here are single nodes; a real target runs three or more. See the Security and Brokers and replication rows in xref:index.adoc#_production_considerations[Production considerations].
