== Why

The migration has to happen underneath a running application, so the application runs first and never stops producing until you decide to. The consumer group matters more than the producer: its committed offsets are the application's memory of what it has processed, and losing them means either reprocessing everything or skipping records. The cutover in xref:finish-cutover.adoc[] is judged on whether those offsets arrive intact.

The producer writes one record every 20 ms on purpose. Redpanda Migrator translates committed offsets by timestamp, and with records that far apart every offset maps to exactly one record on the target, which lets this solution assert the translation exactly. Real workloads write faster than that; the Idempotency and delivery row in xref:index.adoc#_production_considerations[Production considerations] says what changes.

== Why Redpanda

The producer and the consumer are Redpanda Connect configurations, so the "legacy application" is two YAML files with no build step, and the same consumer file runs against either cluster by changing two environment variables. `schema_registry_encode` and `schema_registry_decode` handle the wire format, and the `redpanda` output and input speak SASL/SCRAM to any Kafka-compatible cluster. See xref:connect:components:processors/schema_registry_encode.adoc[] and xref:connect:components:inputs/redpanda.adoc[].

== What happens inside

The producer's `generate` input fires every 20 ms; the Bloblang mapping picks a topic by the record counter (every tenth record an alert, every fifth a customer profile, every third an inventory event, the rest orders) and a key that fits the topic, so the compacted topics compact on the right key. `schema_registry_encode` fetches the subject's latest schema once, caches it, and writes the five-byte wire header (magic byte and schema ID) in front of the Avro bytes. The broker assigns each record a timestamp on arrival.

The consumer joins `orders-service` with the cooperative-sticky balancer, gets all twelve partitions, decodes each record by the schema ID in its header, and commits its offsets every second, which is why `make workload` waited for twelve committed offsets before returning. From here on, `rpk group describe orders-service` on the source is the number the cutover has to preserve.

`STATE Stable` with one member; the lag is whatever the consumer has not read in the last second. If the state is `Empty` or the group does not exist, the consumer could not connect: `docker compose logs orders-consumer` shows whether it was authentication (a changed password in `.env` after the first `make up`) or a missing topic (`make topics` first). If the producer logs `subject not found`, run `make schemas`.

== In production

[.production-note]
Inventory every consumer group on the source before the migration (`rpk group list`, then `rpk group describe`) and decide the order in which they move. Each group is its own cutover. See the Consumer scaling row in xref:index.adoc#_production_considerations[Production considerations].
