== Why

Each step's Verify section checked one thing. This one checks that the clusters agree with each other, which is the claim a migration makes: every topic with the same shape, every record, every schema under the same ID, every committed offset carried over, and the security posture intact on both sides. The negative checks matter as much as the positive ones: an unauthenticated client is refused, the migrator user cannot write to the source or create topics outside `shop.` on the target.

The checks are exact because the workload is designed for it: the producer has stopped, so high watermarks are fixed numbers; records are 20 ms apart, so translated offsets equal the source's; schemas were registered in a known order, so the IDs are known.

== Why Redpanda

Every number the script needs is observable from outside through `rpk`: high watermarks from `rpk topic describe -p`, configurations from `-c`, committed offsets and lag from `rpk group describe`, schemas from `rpk registry schema list`, mode from `rpk registry mode get`, and ACL behaviour from a refused request. That is what makes a migration verifiable rather than trusted. See xref:streaming:reference:rpk/rpk-group/rpk-group-describe.adoc[].

== What happens inside

The script runs each `rpk` command inside the helper of the cluster it inspects, with a `retry` where the migrator may be a batch behind, and compares the source's answer with the target's as strings. Each check prints `ok` or `FAIL`, and `verify_summary` prints `PASS (14/14)` and exits 0, or lists the failed checks and exits 1. CI gates on that exit code.

A failed check names what it compared. The likely ones: `high watermarks match` fails while the producer is still running (finish xref:finish-cutover.adoc[] first), and `mode is READWRITE` fails if you skipped `make sr-readwrite`.

When you are done, `make clean` stops both clusters and deletes their volumes.

== In production

[.production-note]
Keep this script's comparisons as your acceptance test for each migrated topic and group, and keep the source cluster until they pass on the last one. See the Observability row in xref:index.adoc#_production_considerations[Production considerations].
